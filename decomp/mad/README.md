# Декомпиляция видео NFS3: декодер MAD, вывод кадра, плеер

Ролики Need for Speed III (`fedata\movies\titleav.mad`, `demoav1..3.mad`) в порте
сейчас играет перекомпилированный код на виртуальном x86. Здесь та же часть игры,
вручную переписанная на C99 и сверенная с оригинальным машинным кодом
`nfs3.exe` бит в бит.

**В сборку игры это пока не подключено.** Папка самостоятельная: исходники, тесты
против оригинала, листинги и результаты. Подключение к порту — следующий шаг (см.
в конце).

## Что в папке

| Путь | Что |
|---|---|
| `src/mad_decoder.c/.h` | Декодер MAD: коды, коэффициенты, обратное ДКП (AAN), предсказание, вывод строк. 13 функций |
| `src/mad_display.c/.h` | Программный вывод: YUV 4:2:2 → 15/16-бит RGB, 1x и 2x с интерполяцией. 7 функций |
| `src/mad_player.c/.h` | Плеер `showmad`, очередь кадров `initrender`, часы, обёртка `sub_4960e0`. 13 функций |
| `src/mad_tables.h` | Таблицы и константы, вынутые из `nfs3.exe` (`tools/extract_tables.py`) |
| `asm/` | Листинги всех декомпилированных функций (`tools/disx.py`) |
| `tests/` | Дифференциальные тесты: оригинал в Unicorn против этого C |
| `tools/` | Дизассемблер, извлечение таблиц, сборка библиотек для тестов |
| `results/` | Логи прогонов, на которые ссылается этот README |

## Как проверить самому

Нужны Python 3.9+, `gcc` или `clang` (на Windows — MinGW или WSL), и сам
репозиторий: тесты берут `nfs3hp/nfs3.exe` и список функций из
`src/nfs3hp/disassembly/`.

```bash
cd decomp/mad
python -m pip install -r requirements.txt      # capstone, unicorn
python tools/build_libs.py                     # build/libmad*, libmaddisp*, libmadplay*

python tests/diff_decoder.py                   # декодер, ~5 с
python tests/diff_display.py                   # вывод кадра, ~10 с
python tests/diff_player.py --movies 6         # плеер целиком, ~15 с
```

Каждый тест печатает таблицу `cases / fails`; `fails` везде должен быть 0, код
возврата 0. Больше прогонов: `--scale 10` (декодер, вывод), `--movies 40`
(плеер), другое зерно — `--seed N`, x87 в 64-битном режиме — `--cw 0x37f`.

Дополнительно:

```bash
python tests/precision_impact.py              # видно ли разницу 53/64 бит x87 на пикселях
python tests/mutation_check.py                # ловит ли тест декодера ошибки (11 мутаций)
python tests/mutation_display.py              # то же для вывода (8 мутаций)
python tests/mutation_player.py               # то же для плеера (12 мутаций)
python tools/build_libs.py --ubsan && python tests/diff_decoder.py --lib build/libmad_ubsan.so
gcc -O2 -ffp-contract=off -o build/fma_search tests/fma_search.c -lm   # поиск входов для FMA-теста
```

`tools/disx.py 0x4f3600` — листинг любой функции `nfs3.exe` прямо из бинарника.
Если папка лежит не в `decomp/mad` репозитория, укажи корень через `NFS3_REPO`.

## Как устроена проверка

Оригинальные функции из `nfs3.exe` выполняются в Unicorn (эмулятор x86 на базе
QEMU, с настоящим x87), декомпилированные — нативно. Обе стороны получают одно и то
же, после каждого шага сравнивается всё:

- **декодер** — всё состояние (0x9f0c38..0x9f254c, блок коэффициентов, буфер ДКП)
  и каждый байт вывода. Потоки MAD собирает `tests/madstream.py` из таблиц кодов
  самой игры: все коды таблиц A и B, escape, все типы макроблоков, векторы,
  целые кадры. Плюс потоки из случайных байтов;
- **вывод** — таблицы цвета и каждый байт поверхности 640x480: все режимы,
  отсечение, 15/16 бит, невыровненное начало поверхности;
- **плеер** — весь `showmad` в Unicorn с настоящим декодером под ним; всё, что он
  вызывает снаружи (поток EA, звук EA, память, `GetTickCount`, дисплей,
  клавиатура), заменено одинаковыми скриптовыми заглушками. Сравниваются порядок и
  аргументы внешних вызовов, содержимое каждого показанного кадра и итоговое
  состояние плеера.

## Форматы

**Блок видео** в потоке EA:
`+0x00` тег `MADk` (ключевой) / `MADm` (разностный) / `MADe` (разностный, от него
ничего не предсказывается — плеер может его выбросить); `+0x0c` длительность кадра,
мс в 16.16; `+0x10`/`+0x12` ширина/высота (int16); `+0x15` квантователь; `+0x18`
битовый поток.

**Битовый поток**: 16-битные слова little-endian, старший бит первым. Макроблок в
разностном кадре: `00` — всё кодировано; `1` + вектор — всё предсказано; `01` +
6 бит маски + вектор — по блокам. Коэффициенты: DC 8 бит, коды MPEG-1 (B.14),
escape `000001` + уровень:10 + run:6, конец блока `10`. Порядок обхода —
транспонированный зигзаг.

**Выход декодера** — не RGB: упакованный YUV 4:2:2, по 32 бита на два пикселя,
байты `Cr, Cb, Y правого, Y левого`, каждая компонента 7 бит (0..127).

**Цвет** (`sub_4fda20`): BT.601 — `R = 2(y + round(1.402·Cr')) + 1`,
`G = 2(y + round(−0.3441·Cb') + round(−0.7141·Cr')) + 1`,
`B = 2(y + round(1.772·Cb')) + 1`, где `C' = C − 64 + 0.5`; затем 5/6 бит,
левый пиксель пары округляется, правый усекается (двухпиксельный дизеринг).

## Найдено по пути

- **В роликах всегда программный вывод**: плеер открывает дисплей с флагом 1, путь
  через оверлей DirectDraw не используется. Режим 1/2/3 — по частоте CPU (<133 МГц,
  <200 МГц, иначе); порт сообщает 2 ГГц, так что в порте режим 3, полная
  интерполяция 2x.
- **Кадры MADe почти всегда выбрасываются**: в программном режиме плеер сам ставит
  флаг пропуска, так что после предзагрузки (до 6 кадров) MADe не декодируются.
  Ролики на ПК шли с пониженной частотой кадров — нативный плеер может
  показывать их плавнее оригинала.
- **Ошибка оригинала**: в таблице ограничения значение 127 не заполнено и даёт 0 —
  самый яркий отсчёт становится чёрным. Повторено как есть.
- **x87**: обратное ДКП округляет через «магическое число» 1,5·2⁵²; результат
  зависит от точности x87. C считает в `double` = 53 бита — как эмулятор порта.
  Игра перед первой гонкой делает `fninit` (64 бита), так что на ПК ролики после
  гонки идут в 64 битах; на пикселях разницы не найдено.

## Где C сознательно отличается от оригинала

Только там, где оригинал портит память или читает мусор; на корректных данных
поведение то же:

- `mad_decode_block`: на испорченном потоке оригинал пишет коэффициенты за блок по
  мусору после таблицы обхода. Здесь — флаг `overflow` и выход из блока.
- `mad_show_frame`: строка шире 321 слова в режиме 3 переполняла буфер на стеке
  оригинала (0xa00 байт). Здесь — возврат −3.
- `mad_player_play`: если ролик начинается не с ключевого кадра, оригинал читает
  опорный кадр по неинициализированному указателю. Здесь берётся сам кадр.
- Только little-endian (x86, arm64): декодер, как и оригинал, адресует байты внутри
  32-битных слов.
- Собирать без FMA (`-ffp-contract=off`): иначе обратное ДКП может разойтись с
  оригиналом в целой части (`tests/idct_critical_rows.txt`, 35 найденных случаев).
